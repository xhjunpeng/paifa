# Paifa 连续执行与按需派发设计

**日期：** 2026-08-07  
**状态：** 已获方向批准，待实现计划  
**范围：** Paifa skill 的触发语义、派发决策、派发回收和测试契约；不在本次变更中实现通用 DAG、并行任务图、可视化或常驻服务。

## 问题与目标

Paifa 当前把“下一步会改变状态”作为触发条件，并在路由信息不可见时把工作导向内部子智能体或独立任务。这使普通开发也被拆成派发任务。派发者和接收者之间又没有可验证的唤醒与回传契约，因此模型在一次回复结束后无法自行开始下一步，造成“声称会继续、实际需要用户再次输入继续”的体验。

本设计的目标是让一个普通任务由主任务连续完成；只有派发的并行收益明确大于交接成本、并且系统能可靠收回结果时，才派发。人只会在真正的 Gate（需要审批、业务选择、生产/付费/凭据或不可逆操作）或任务完成时被打断。

## 已选择的方向

采用“主任务优先 + 动态派发决策 + 可验证连续性”的三层模型。

1. **执行层：** 主任务默认直接执行（`direct`），持有上下文并负责实现、调试、测试、整合与完成。
2. **决策层：** 仅当准备派发、需要模型升级，或触及高风险边界时调用 Paifa。决策输出 `direct`、`subagent` 或 `task`，而非一律输出派发路由。
3. **连续性层：** 仅对实际派发建立父任务等待、回传、checkpoint 和恢复协议。没有可靠回传/唤醒能力时，非必要派发必须被拒绝并回退为 `direct`。

不采用“所有变更必经派发”的方案：它减少的不是工作量，而是把上下文理解、交接与整合重复多次，通常增加 token 与中断。

## 术语与边界

| 术语 | 定义 |
| --- | --- |
| `direct` | 主任务在当前上下文直接执行；不创建子智能体或独立任务。 |
| `subagent` | 有界、可独立回收的内部子智能体；主任务保持活跃并等待其结果。 |
| `task` | 需要独立 worktree、侧栏可见性、直接用户跟进或独立复审的外部任务。 |
| 连续性保障 | 派发后，父任务可被结果事件可靠唤醒并能恢复到正确状态的能力。 |
| Gate | 必须暂停给用户的边界：Sol 审批、业务方向、生产、凭据、付费服务或不可逆删除/迁移。 |
| checkpoint | 足以在会话中断后恢复派发治理状态的持久事实记录；不是重新执行已完成节点的许可。 |

本设计不承诺模型能够在一次已结束的宿主回合之外自行开启新回合。宿主没有提供可靠唤醒能力时，系统必须如实降级为主任务直做或停在明确 Gate，不能用“将自动继续”替代真实执行能力。

## 触发语义

Paifa 的全局安装块、`SKILL.md` 和 routing policy 统一改为：

> 只有在考虑真实派发、模型升级或高风险边界时调用 Paifa。普通的直接编辑、测试、调试、重试和整合由当前主任务连续执行。

因此，“修改文件”“运行测试”“写普通计划”本身不再触发 Paifa。若这些工作已处于一个获批/已启动的任务信封内，也不重新作出派发决定；仅在任务目标、仓库、风险边界或派发事实发生变化时重新评估。

Sol 的审批要求不改变：只有高后果且高不确定，或有证据表明 Terra/high 失败时，才进入 Sol Gate。此规则是模型升级治理，不是要求把工作交给子任务的理由。

## 动态派发决策

每次可能派发时，主任务按下列四项给出基于事实的判断，而不是按文件数、时长、关键词或静态分数判定。

| 判断项 | 可派发的必要条件 | 不满足时的结果 |
| --- | --- | --- |
| 独立性 | 目标、允许/禁止范围、输入事实、验收命令和停止条件足以让受托者完成；预计不需与主任务来回澄清。 | `direct` |
| 并行收益 | 受托工作能与主任务另一项有价值工作同时进行，或独立复审/隔离带来的收益明确。 | `direct` |
| 交接成本 | 准备事实包、受托者重新理解、回传和整合的预计成本小于主任务直接完成。 | `direct` |
| 连续性保障 | 已验证有结果回传与父任务接收/恢复路径；父任务不会在结果前终止为最终回复。 | `direct`，除非这是必须由用户显式要求的独立任务。 |

四项必须同时满足才能选择派发。派发种类随后才决定：需要共享当前目录且可在父任务活跃期间回收结果时选 `subagent`；只有独立 worktree、侧栏持久性、用户直接跟进或独立复审确有必要时才选 `task`。`task` 也必须满足连续性保障，不能把“以后让用户说继续”当作回收机制。

决策记录必须包含：候选工作、四项事实和结论、选择的 mode、模型/思考强度（仅实际派发时）、父任务的回收方式及停止条件。`direct` 记录简短结论即可，且不得伪造不可见模型能力；直接执行不因当前模型元数据不可见而被强制转换为派发。

## 派发连续性协议

实际派发使用一个由主任务拥有的 `DispatchRecord`，作为任务信封的扩展。最小字段如下：

```text
run_id                 稳定的派发批次标识
dispatch_id            单次派发标识
parent_id              父任务标识
mode                   subagent | task
state                  proposed | running | waiting | succeeded | failed | blocked | cancelled
route                  实际执行者的模型、思考强度与派发方式
fact_envelope          已验证的紧凑事实包
return_contract        回传格式、验收证据、回传事件来源
resume_checkpoint      已保存的父任务控制事实和下一个决策点
attempt                从 1 开始的尝试次数
created_at/updated_at  可审计时间
```

状态转换只允许如下路径：

```text
proposed → running → waiting → succeeded | failed | blocked | cancelled
failed   → running       （仅主任务根据原任务信封内的安全重试决定）
blocked  → running       （仅 Gate 已解除且未超出已批准范围）
```

`waiting` 的含义是“主任务仍在等待并持有接收责任”，不是向用户输出最终答复。开始派发前，主任务必须先保存 checkpoint，再启动受托者；收到回传后，按 `dispatch_id` 和 `attempt` 去重，原子写入终态和证据，再由父任务整合并重新执行动态派发判断。迟到、重复或无法匹配的回传不得覆写已保存输入，也不得触发第二次整合。

父任务中断后，恢复流程读取 `DispatchRecord`：`succeeded` 只整合已记录的证据，绝不重跑；`running`/`waiting` 先查询或等待同一 `dispatch_id` 的状态，不能盲目新建重复工作；身份、仓库、凭据或证据冲突时转换为 `blocked` 并安全停止。取消会写入 `cancelled`，此后禁止启动新节点，并忽略仅会造成副作用的迟到回传。

## 宿主能力与降级

新增一个明确、可测试的宿主能力检查，而不是从工具名称推断能力：

| 能力 | 含义 | 对派发的影响 |
| --- | --- | --- |
| `result_return` | 受托者能够带 `dispatch_id` 返回结构化结果。 | 缺失则禁止派发。 |
| `parent_wait` | 父任务能在同一活跃执行中等待结果而非结束回合。 | 缺失则禁止 `subagent`。 |
| `parent_wake` | 结果事件能唤醒/继续父任务，或运行器承诺由 checkpoint 恢复父任务。 | 缺失则禁止需要跨回合回收的 `task`。 |
| `checkpoint_store` | 可原子保存和读取 `DispatchRecord`。 | 缺失则禁止可中断的派发。 |

当能力不足时，决策结果为 `direct`，并继续由主任务完成；不得先创建受托者，再发现无法回收。若用户明确要求独立任务但能力不足，主任务应说明具体缺失的能力并请求方向，而非承诺自动续跑。

实现必须区分“父任务当前可等待的内部子智能体”与“独立侧栏任务可能稍后完成”。后者在没有 `parent_wake` 和 `checkpoint_store` 时不可选。任何面向用户的进度文字必须反映实际状态：只有已经进入 `waiting` 且回传路径受验证时才可说“正在等待结果”；没有 wakeup 时不得说“会自动进入下一项”。

## 组件改动

| 组件 | 责任变化 |
| --- | --- |
| `SKILL.md` | 把状态变更触发替换为派发/升级/高风险触发；说明 `direct` 默认和四项判断。 |
| `templates/global-agents-block.md` | 安装到用户全局规则的简版决策门禁，与 `SKILL.md` 语义一致。 |
| `references/routing-policy.md` | 先选执行模式、再对实际派发选择模型和强度；保留 Sol Gate，不再用“模型元数据不可见”强制派发。 |
| `references/tool-mapping.md` | 记录能力探测、回传与恢复需求，而不是把 “continue task” 当成天然可用的自动唤醒。 |
| `templates/task-envelope.md` | 保留事实包，同时增加可选的派发回收契约字段；`direct` 不需要信封。 |
| `scripts/lib/dispatch-capabilities.mjs` | 扩展为读取并验证连续性能力，而非只校验模型能力。 |
| 新的纯决策模块 | 输入任务事实和宿主能力，输出 `direct`/`subagent`/`task` 及理由；不得真正派发。 |
| 新的 dispatch state 模块 | 创建、校验、持久化并去重 `DispatchRecord`；不得含模型选择或 UI 文案。 |
| 调用层 | 先判 mode，再在能力满足时创建派发与 `waiting`；结果回传后恢复父任务的整合循环。 |

目录和 API 的精确文件名由实施计划在核对现有脚本边界后确定，但新模块必须保持“决策纯函数”和“状态持久化”分离，避免让 skill 文案成为运行时状态机。

## 错误处理与用户可见行为

- 普通开发、连续调试、同一模块多步修改：主任务直接推进，期间不要求用户重复输入“继续”。
- 结果回传失败或超时：父任务保留 checkpoint，报告正在等待或已失败的真实状态；可在原信封范围内安全重试，不能启动不受控的第二个相同派发。
- Gate：保留用户确认语义。仅 Gate 或缺少业务方向时停止等待用户；不是为了确认每一项普通开发步骤。
- 验收失败：主任务整合结果、分析失败并继续必要的安全修复；不因失败自动改派给新任务，必须重新做四项判断。
- 恢复时发现风险边界变化：不重跑，转 `blocked`，解释需要的新授权。

## 验收与测试

实现至少覆盖以下可观察行为：

1. 普通、明确的单模块修改选择 `direct`，且不会调用任何派发工具。
2. 同模块的实现、测试、修复链保持主任务连续执行；模型能力元数据缺失不会单独造成派发。
3. 两项真正独立的工作在全部四项成立、且宿主具备 `result_return`、`parent_wait`、`parent_wake`、`checkpoint_store` 时可选 `subagent` 或 `task`。
4. 任一连续性能力缺失时，非必要候选派发回退为 `direct`，并且不会创建受托者。
5. 派发在启动前保存 checkpoint；重复、迟到回传只被整合一次；取消后不再启动新工作。
6. 中断恢复不会重跑已成功派发；身份、仓库或凭据冲突会安全进入 `blocked`。
7. Sol Gate 的触发与“是否派发”解耦，仍只在既定高风险条件下要求一次有效确认。
8. 安装模板、skill、policy、tool mapping 和测试中的措辞一致，且不含“无 wakeup 时自动继续”的承诺。

测试以纯决策单元测试、状态转换/去重测试、能力降级测试和一条端到端模拟回传测试组成。现有路由、审批、安装和生命周期测试应保持通过，并补充回归断言：主任务直做是默认，而不是异常路径。

## 非目标与后续

本阶段不构建 LangGraph 式通用图引擎、不支持任意 DAG 调度、不承诺后台常驻 runner，也不自动创建 worktree。它只为 Paifa 已经会发出的派发决定建立可靠的收回边界。

当宿主提供稳定的跨回合 wakeup 事件后，可以在不改变上述 `DispatchRecord` 契约的前提下，增加持久队列、并行 ready 节点与可视化运行图。它们是第二阶段能力，不能被作为本阶段“自动连续执行”的前提或虚假承诺。

## 设计自检

- **占位符：** 无 `TBD`、`TODO`、待定字段或未指定的成功条件。
- **一致性：** 默认 `direct`、四项全满足才派发、缺连续性即回退三项在触发语义、决策、状态和测试中相同。
- **范围：** 只改变 Paifa 的治理和连续性契约；明确排除通用图运行时与后台服务。
- **歧义：** “自动继续”限定为已验证的回传/唤醒路径；没有该路径时明确为 `direct` 或显式阻塞，不允许由文案暗示自动化。

# Paifa 独立技能设计

日期：2026-08-05
状态：v1.0.0 已实现、验证并完成本地安装
源码位置：`<repo-root>`

## 1. 目标

`paifa` 是 Codex 任务派发前的模型、思考强度、会话和上下文路由守门员。

它的核心目标不是一味选择便宜模型，而是：

> 在满足质量和风险下限的前提下，选择预计总成本最低的模型、思考强度、会话方式和验证方式；当证据表明能力不足时再升级。

`paifa` 同时解决五个问题：

1. 是否真的需要派发。
2. 应创建新任务、继续原任务、创建内部子代理，还是 Fork。
3. 应使用哪个模型和思考强度。
4. 应携带多少上下文，以及如何避免上下文污染。
5. 结果未达标时应修环境、补上下文、重路由，还是升级模型。

由于该 Skill 会在派发时频繁加载，`SKILL.md` 目标控制在 500 个英文单词等量内容以内；评分细节、风险矩阵和工具参数映射按条件加载，避免把完整参考内容带入每次派发。

## 2. 非目标

第一版不负责：

- 实现业务任务。
- 替代 Codex 的任务调度工具。
- 实时计算供应商价格。
- 自动联网更新。
- 建立长期成本数据库或仪表盘。
- 自动修改正在运行任务的模型。
- 为所有低风险任务强制增加 Reviewer。
- 创建另一套 Loop、Graph 或工作流状态机。

## 3. 总体架构

`paifa` 采用“全局薄规则 + 独立 Skill + 可执行校验器”的结构：

```text
全局 AGENTS.md 薄规则
        ↓ 派发前强制触发
paifa Skill
        ↓ 生成路由和质量合同
validate-route 校验
        ↓
Codex 派发工具显式传入可执行参数
        ↓
PAIFA_DISPATCHED 记录真实参数
        ↓
PAIFA_CONTEXT 记录上下文交付证据
        ↓
子任务结果验证与升级判断
```

全局薄规则和 Skill 随同一个仓库发布，但运行时安装在两个位置：

- Skill：`~/.codex/skills/paifa`
- 触发规则：`~/.codex/AGENTS.md` 中带标记的托管区块

薄规则不能只写在 `SKILL.md` 中，因为 Skill 在被调用前无法自行触发。

托管区块同时表达一项有限的持续授权：当用户明确要求“派发、拆分任务、创建子任务或并行处理”时，`paifa` 可以在该目标范围内选择并显式传入具体模型、思考强度和会话方式。该授权不允许创建无关任务、扩大文件或权限范围，也不允许绕过高风险确认。

## 5. Skill 触发范围

`paifa` 必须在以下动作发生前调用：

- 创建独立 Codex 任务。
- 继续一个已存在的委派任务且准备覆盖模型或思考强度。
- 创建内部子代理。
- Fork 一个任务。
- 重试失败、被拒绝或用户不满意的委派任务。
- 用户要求在保证质量的同时使用最低成本模型。

以下情况不触发：

- 普通单任务开发且没有委派。
- 只解释模型区别，没有实际派发。
- 只查看任务状态且不准备重试或继续。

当用户已经指定模型时，`paifa` 走快速风险和兼容性检查；除非低于明确的质量或风险下限，否则尊重用户指定。

## 6. 路由流程

每次运行遵循固定顺序：

1. 判断派发是否必要，以及任务能否安全拆分。
2. 决定会话动作。
3. 应用硬性风险下限。
4. 完成五项轻评分。
5. 选择最低可胜任模型和思考强度。
6. 选择上下文模式并生成事实型任务包。
7. 定义质量合同和完成证据。
8. 定义自动升级上限和升级条件。
9. 输出 `PAIFA_ROUTE`。
10. 使用校验器检查硬规则。
11. 调用真实派发工具并显式传入参数。
12. 输出 `PAIFA_DISPATCHED`。
13. 子任务返回后，根据证据完成、修复环境、补充上下文、重新路由或升级。

## 7. 硬性风险下限

以下领域不经过廉价模型试错：

- 权限、身份、租户隔离、安全：至少 Sol `high`。
- 支付、账单、数据迁移、生产发布：至少 Sol `high`。
- 架构决策和复杂跨模块根因：至少 Terra `high`，通常 Sol `high`。
- 冻结候选、最终 Gate、独立安全验收：Checker 至少 Sol `high`。
- 不可逆操作：除高能力模型外，必须取得用户确认。

硬性下限优先于评分。单文件修改也不能绕过风险下限。

## 8. 五项轻评分

每项使用 `0/1/2`：

| 因素 | 0 | 1 | 2 |
|---|---|---|---|
| 需求清晰度 | 完全明确 | 少量判断 | 模糊或冲突 |
| 模块耦合 | 单文件或孤立 | 同模块多文件 | 跨模块或跨服务 |
| 错误后果 | 易恢复 | 影响功能正确性 | 安全、数据或生产 |
| 验证难度 | 明确自动测试 | 自动测试加人工判断 | 主观或缺少判断标准 |
| 根因不确定性 | 已知机械操作 | 普通诊断 | 未知根因或架构问题 |

默认映射：

```text
0–2  → A：Luna low/medium
3–5  → B：Terra medium
6–7  → C：Terra high；复杂根因可用 Sol high
8–10 → D：Sol high/xhigh
```

评分不以文件数和预计耗时作为硬升级条件。长时间机械任务仍可使用低成本模型；可拆分的大任务优先拆分，而不是整体升级。

内部子代理如果没有 Luna 能力，从 Terra `low/medium` 起步。

## 9. 会话策略

会话动作固定为：

```text
create | continue | spawn-internal | fork
```

默认原则：

> 独立任务默认新会话；同一目标默认继续；上下文污染后使用 clean-room 新会话；只有确实依赖完整历史时才 Fork。

创建新会话的典型条件：

- 独立交付物，可与主任务并行。
- 需要独立工作树、独立证据链或用户长期查看。
- 需要与主任务不同的模型。
- 主任务历史很长而子任务只需要少量事实。
- Maker 和独立 Checker 必须隔离。

继续原会话的典型条件：

- 目标、范围和工作目录未变化。
- 同一根因的第一次或第二次修复。
- 补充上下文、补跑验证或提高下一轮模型等级。

创建 clean-room 新会话的典型条件：

- 两轮同根因修复仍不收敛，并发现错误假设。
- 原任务范围发生实质变化。
- 原上下文被大量错误假设污染。
- 内部子代理需要更换模型。

Fork 只用于依赖原会话大部分决策历史的分支探索。Fork 不用于节省历史 Token，也不用于消除上下文污染。

## 10. 上下文策略

上下文模式：

```text
minimal | compact | recent | full-required | clean-room
```

任务包应传递事实，不传递未经证实的根因假设：

```text
目标：
工作目录：
允许修改：
禁止修改：
已验证事实：
尚未确认：
验收命令：
停止条件：
返回格式：
```

新会话是否省 Token 取决于历史复用价值与重新启动成本。`paifa` 使用三个附加因素判断：

- `context_dependency`：对原会话事实和调查结果的依赖。
- `pollution_risk`：错误假设、范围漂移和反复失败风险。
- `bootstrap_cost`：新会话重新理解项目所需成本。

## 11. 质量合同

每次派发前必须定义“怎样才算完成”。根据任务类型选择证据：

- 代码：测试、类型检查、构建、精确 diff。
- 调查：复现步骤、来源、因果证据和已排除项。
- UI：截图、真实交互、响应式和必要的多语言检查。
- 安全：权限边界、租户隔离、负面测试和独立复核。
- 文档：完整性、链接和术语一致性。

没有可靠质量合同时，不得直接派发。若缺失内容会改变风险或结果，先请求用户补充；否则使用最小可验证证据并明确剩余风险。

## 12. 升级状态机

```text
评估任务
  → 选择最低可胜任模型
  → 执行
  → 验证
      ├─ 达标：完成
      └─ 不达标：诊断
          ├─ 环境、权限、工具问题：修环境，不升级
          ├─ 任务说明不清：补任务包，不升级
          ├─ 范围变化：重新路由
          ├─ 模型能力不足：升级一级
          └─ 超过自动上限或高风险：请求用户确认
```

普通独立任务的默认升级阶梯：

```text
Luna low
→ Luna medium
→ Terra medium
→ Terra high
→ Sol high
→ 用户确认后 Sol xhigh/max/ultra
```

允许自动升级的证据包括：

- 明确要求已写清，但模型持续遗漏关键要求。
- 同一根因连续两轮修复仍失败。
- 输出自相矛盾或无法解释实现与验证结果。
- 只修表面现象，没有处理已明确的根因。
- 上下文足够时仍持续定位错误模块或依赖。
- Checker 给出实质性质量问题。
- 声称完成，但指定验证实际失败。

自动升级上限为 Sol `high`。`xhigh/max/ultra` 或不可逆、高风险动作需要用户确认。

## 13. 固定输出

A/B 类快速回执：

```text
PAIFA_ROUTE v1 | create | B | terra/medium | compact | focused-tests | auto<=sol/high
```

C/D、风险或重试任务使用扩展 YAML，至少包含：

- 版本和阶段。
- 会话动作和派发类型。
- 角色与任务等级。
- 五项评分和风险下限。
- 模型、思考强度和上下文模式。
- 质量合同。
- 自动升级上限与原因。

真实派发后必须记录：

```text
PAIFA_DISPATCHED | model=gpt-5.6-terra | effort=medium
PAIFA_CONTEXT | mode=compact | delivery=envelope:sha256:<hash>
```

`PAIFA_ROUTE` 表示计划；`PAIFA_DISPATCHED` 只记录工具实际接收的模型、思考强度和内部子代理 `forkTurns`。这些可执行字段必须与计划一致。上下文模式不是独立工具字段，使用 `PAIFA_CONTEXT` 另记事实信封的标识或哈希，不能伪装成工具返回值。

## 14. 工具映射

`tool-mapping.md` 维护 Codex 工具差异：

- 新建任务使用模型字段和 `thinking`。
- 继续已有任务可在下一轮覆盖模型和 `thinking`。
- 内部子代理使用模型字段和 `reasoning_effort`。
- 内部子代理覆盖模型时不能依赖完整历史继承。
- Fork 本身不直接完成模型选择，需要在后续任务消息中显式覆盖。

模型和支持的思考强度可能变化。Skill 优先读取当前派发工具支持的组合，不把价格和全部模型列表永久硬编码在主入口中。

如果推荐组合不可用，只能选择满足同一质量下限的最低成本替代；不得静默降到质量下限以下。

## 15. 校验器

`validate-route.mjs` 只校验确定性硬规则，不替代语义评分：

- 路由是否包含模型和思考强度。
- 模型是否支持该思考强度。
- 高风险任务是否低于能力下限。
- 自动升级是否超过 Sol `high`。
- `xhigh/max/ultra` 是否获得确认。
- 独立 Checker 是否使用干净新会话。
- 模型覆盖时是否错误携带完整历史。
- Fork 是否被错误用于上下文清理。
- 是否存在质量合同。
- 真实模型、思考强度和内部子代理 `forkTurns` 是否与计划一致。
- 实际回执是否错误包含不存在的上下文工具字段。

校验失败时禁止派发，并返回具体修复建议。

## 16. 安装、修复、升级和卸载

本地开发默认使用符号链接：

```text
~/.codex/skills/paifa
    → <repo-root>
```

公开用户可以克隆仓库后运行安装脚本。安装流程必须：

1. 解析明确目标路径。
2. 检查现有安装和全局规则冲突。
3. 备份 `~/.codex/AGENTS.md`。
4. 创建或更新 Skill 符号链接。
5. 安装带版本标记的全局薄规则。
6. 运行 doctor。
7. 任一步失败时恢复修改前状态。

全局规则采用托管标记：

```text
<!-- PAIFA_MANAGED_BLOCK_START version=1 -->
...
<!-- PAIFA_MANAGED_BLOCK_END -->
```

安装和升级只修改标记区块，不能覆盖用户其他全局规则。重复安装必须幂等，不能产生重复段落。

建议命令：

```bash
./scripts/install.sh
./scripts/install.sh --update
node scripts/doctor.mjs
./scripts/uninstall.sh
./scripts/uninstall.sh --restore-backup
```

第一版不自动联网更新。升级由用户显式执行 `git pull` 和安装更新命令。

第一版安装器支持 macOS 和常见 Linux shell 环境。Windows 安装属于后续独立能力，README 必须明确这一边界，不能把 Bash 安装器描述为全平台支持。

## 17. Doctor 检查

`doctor.mjs` 检查：

- Skill 链接是否存在且指向预期目录。
- `SKILL.md` 和 frontmatter 是否有效。
- 全局托管区块是否存在、唯一且版本匹配。
- 参考文件、模板、脚本和评测文件是否完整。
- 路由案例文件和触发案例文件的格式是否有效。
- 确定性校验器的固定案例是否通过。
- 安装是否处于半完成状态。

Doctor 只报告和建议修复；涉及覆盖、删除或恢复全局文件时必须由用户显式执行修复命令。

Doctor 不声称证明模型一定会触发 Skill，也不声称证明语义评分永远正确。触发行为和语义路由必须通过独立的模型压力测试验证。

## 18. 验收测试

路由评测至少覆盖：

1. 单文件机械修改使用低成本模型。
2. 长时间重复任务不因耗时升级。
3. 单文件权限修改仍进入高风险等级。
4. 普通单模块开发选择 Terra `medium`。
5. 跨模块未知根因选择 Terra `high` 或 Sol `high`。
6. 环境错误不触发升级。
7. 上下文不足不触发升级。
8. 两轮同根因失败自动升级。
9. 范围变化触发重新路由。
10. 独立 Checker 使用 clean-room 新会话。
11. 单纯模型升级继续原会话。
12. 内部子代理换模型时创建新代理。
13. Fork 不用于清除上下文污染。
14. 用户指定低于风险下限的模型时发出警告。
15. 推荐参数与实际派发参数不一致时失败。
16. 模型不可用时不允许静默降级。
17. 可拆分的机械大任务不整体交给 Sol。
18. 无质量合同时禁止派发。

触发评测覆盖：

- 应触发：派发、并行、创建子任务、内部子代理、失败重试、最低成本模型路由。
- 不应触发：普通开发、只回答问题、不涉及实际派发的模型讨论。

评测分为两层：

- 确定性测试：由脚本验证输入、输出、风险下限、安装幂等和参数一致性。
- 模型压力测试：用代表性提示词验证是否触发、是否选择合理路由、是否会在环境失败时错误升级。

模型压力测试结果必须记录模型、思考强度、用例版本、实际输出和判定，不能只保存“通过”结论。

## 19. GitHub 发布安全边界

仓库不得包含：

- 本地用户名和硬编码绝对路径。
- 私有项目源码、任务记录或内部业务规则。
- API Key、账户信息和真实模型用量。
- 用户个人 `AGENTS.md` 全文。
- 私有任务提示词和敏感测试数据。

安装脚本运行时探测用户目录，公开源码只使用参数、环境解析结果或 Git 根目录。

仓库内的 `docs/design.md` 必须使用 `<repo-root>`、`$HOME` 等可移植占位方式；本设计稿中的用户本地计划路径不能原样进入公开发布文档。

## 20. 完成标准

第一版只有同时满足以下条件才可宣布完成：

- 独立仓库结构完整。
- `SKILL.md` 保持在 500 个英文单词等量内容以内，复杂规则按需加载。
- 全局规则安装、重复安装、升级、卸载和备份恢复经过验证。
- Doctor 和校验器具有明确成功与失败输出。
- 确定性路由测试和安装测试全部通过。
- 模型触发与语义路由压力测试具有可复核记录并达到预设通过标准。
- 高风险任务不会被错误降级。
- 环境、权限和上下文问题不会被误判为模型能力不足。
- 实际派发参数可与计划路由核对。
- README 包含安装、使用、升级、修复、卸载和安全边界。
- 没有私有路径、凭证或项目数据进入发布包。

## 21. 已确认决策

- 名称使用 `paifa`。
- 采用全局薄规则、独立 Skill 和校验器的组合。

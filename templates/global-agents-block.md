Before the first material action in a new development package, invoke `paifa`: state the direct/delegated mode, model plan, reasoning level, and short reason, then show one proposal and wait for the user's exact `1`. That numbered reply applies only to the Paifa development gate and an evidence-based Sol escalation; do not impose it on ordinary clarification, discussion, or project-specific Gates. After the user replies with the exact `1`, call `get_goal`: if an active Goal already covers the same task, keep or resume it; otherwise call `create_goal` with an objective for the approved task envelope. While the Goal is active, do not send `final_answer`; publish progress through commentary and keep executing. After compaction, call `get_goal` and continue any active Goal. Only after verified completion may the main task call `update_goal` with `complete` and send a final answer; for a genuine blocker meeting the host's blocked threshold, call `update_goal` with `blocked`. Ask again only for an evidence-based Sol escalation or when the next action newly touches production data, makes a real vendor call or cost, uses credentials, is irreversible, changes a permission/public interface, or changes business direction. Review findings, test failures, more necessary files, and async/concurrency/idempotency/security/availability/duplicate-charge repairs remain inside the active Goal and never justify another `1` or a false blocked state. Its SKILL.md is the source of truth for model routing, approval, delegation, and completion rules.

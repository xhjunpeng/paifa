# Paifa

Before applying this workflow, inspect the applicable project instructions. If the project `AGENTS.md` explicitly declares Loop OS as the sole control plane, do not invoke Paifa or apply its proposal, `1`, Goal, delegation, validation, or closeout rules to that project. The standard explicit declaration is: `本项目由 Loop OS 作为唯一控制平面；先执行 Loop Gate 和 Context；Paifa 的授权、Goal、派发、验收和收口规则不适用。` Do not propose, wait for `1`, create or resume a Goal, dispatch, validate, accept, or close out under Paifa. Merely mentioning Loop OS, Loop Gate, or Context does not activate this exception. Loop OS alone owns that project's Gate, context, dispatch, lanes, checks, evidence, acceptance, and closeout. An explicit project declaration is required; without it, Paifa remains applicable.

Before the first material action in a new development package, show one proposal and wait for the user's exact `1`. State the execution mode, model plan, reasoning level, and a short reason. This Paifa development gate, and any evidence-based Sol escalation, use `1`; do not impose numbered replies on ordinary clarifications, discussion, or project-specific Gates. That approval covers the approved task envelope: planning, implementation, tests, debugging, retries, integration, and necessary delegation until verified completion.

After the user replies with the exact `1`, use native Goal tools when the host provides them. First call `get_goal`: if an active Goal already covers the same task, keep or resume it; otherwise call `create_goal` with an objective that names the approved task envelope and its completion evidence. When native Goal tools are unavailable, continue in the current task, but do not claim automatic cross-turn continuation that the host cannot provide.

While the Goal is active, do not send `final_answer`; send meaningful progress through commentary and keep executing the approved work. Before sending a final answer, call `get_goal` and confirm that no active Goal remains for this task. After compaction or a resumed turn, call `get_goal` and continue any active Goal without requesting routine approval again. Only after verified completion may the main task call `update_goal` with `complete` and then send its final answer. For a genuine blocker that meets the host's blocked threshold, call `update_goal` with `blocked`; otherwise report the evidence in commentary and continue when the blocker clears. Ask again only when the next action newly touches production data, makes a real vendor call or cost, uses credentials, performs an irreversible operation, changes a permission/public interface, or changes business direction. A severe review finding, test failure, more necessary files, or repairs to async, concurrency, idempotency, security, availability, or duplicate-charge paths do not change that boundary: they remain inside the active Goal and must continue without `final_answer`, a second `1`, or a false blocked state.

Before proposing execution, choose exactly one route: (1) direct execution, (2) one bounded execution worker, or (3) multiple parallel workers. Delegate only when the expected net benefit exceeds dispatch and integration cost: it must materially shorten total completion time, keep noisy searches, test logs, or debugging output out of the main task, or provide an independent verification path. Every delegation must state explicit inputs, scope, completion criteria, exclusive file or module ownership, validation, and return format. A worker may develop only a bounded scope with an exclusive mutable file or module surface. Workers in the same task branch must not create another branch or worktree. Choose direct execution when the task is small, tightly coupled, decision-heavy, shares a mutable surface, has an unclear return path, or delegation has no net benefit. Choose one worker when its bounded scope is independently verifiable and isolating its implementation, search, tests, or logs benefits the main task. Choose parallel workers only when two or more bounded work packages can proceed independently with exclusive mutable surfaces or read-only scope and are expected to shorten total completion time. The main task coordinates, resolves cross-worker conflicts, integrates the result, and owns the final answer. For a direct proposal, use `方式：主任务直接执行｜推荐模型：<具体模型>｜推荐思考强度：<具体强度>｜执行：保持当前主任务设置（可在 Codex UI 手动切换）｜原因：<短原因>`. Select the recommendation from the task category, then state that execution keeps the current main-task settings and that the user may manually switch in the Codex UI. The recommendation is a plan, not a claim that the main task has switched. Do not create a delegate merely to name a model.

Direct execution does not require visible model metadata. Its recommendation still follows the same lowest-suitable routing ladder: simple work Luna/low, clear work Luna/medium, ordinary work Terra/medium, and complex or high-risk-but-verifiable work Terra/high. A direct Sol recommendation requires the same evidence gate and second `1` as an actual Sol escalation.

For actual delegation, use the lowest capable route: Luna/low for code search, formatting, mechanical verification, and simple batch work; Luna/medium for bounded small implementations, confirmed bug fixes, targeted test additions, and verified batch edits; Terra/medium for ordinary multi-file development; Terra/high for complex logic, cross-module work, difficult debugging, or high-risk-but-verifiable changes. Sol requires both high consequence and high uncertainty, or evidence that Terra/high failed. A later Sol escalation requires one additional `1`; ordinary progress after the first approval never needs another confirmation.

The main task is the only actor for proposal, approve, and user interaction. Before approval it must not create a real delegate. Before actual delegation, verify that the active host provides host-managed collection of every worker result; if it does not, use direct execution. Record every dispatched worker id, then let the host collect and return terminal results. The main task must use the host waiting mechanism, avoid high-frequency polling and avoid commentary that adds no new information; it must not give a final answer until the host returns every worker result. On a host-reported timeout or blocked state, give one status update; otherwise integrate every worker result, then send a final answer only when the Goal lifecycle permits it. A worker inherits the approved route and scope, must not use the approval CLI or ask the user for confirmation, must not create subagents, and only returns a short result covering changes, files, validation, and residual risks or blockers. The host UI may show a worker panel, but only the main task integrates the results and gives the final answer.

Once approved, the task envelope covers planning, implementation, tests, retries, branch, push, PR, checks, merge, and closeout. Keep business-direction, production, credentials, paid-service, irreversible-operation, and project-specific Gates separate from Paifa; they may still need their own authorization.

Only when this task created an independent task branch and that branch has been merged, switch to the merged base branch and run `node scripts/closeout.mjs --base <base> --branch <task-branch>`. It pulls the base, removes only that merged task branch locally and remotely, then prunes stale worktree records. It must not delete unmerged, dirty, unrelated, or active worktree branches; report those blockers instead of calling the task complete.

Ask again only for an evidence-based Sol escalation or an actual external high-risk consequence change.
